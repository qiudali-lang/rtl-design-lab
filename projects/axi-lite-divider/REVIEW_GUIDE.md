# AXI read-response fix: project review guide

本记录用于区分原始实现和 2026 年 9 月作品集整理时增加的测试与修复。

## 1. 原来已经完成了什么

原版实现了 AW/W 独立接收、寄存器写入、BVALID 保持、start/ack 脉冲、8-bit 迭代除法器及 MicroBlaze 集成。除法器逻辑未因本次整理而修改，新枚举测试覆盖全部 65,280 组非零除数输入。

## 2. 原读路径为什么有问题

原版 `always_comb` 直接用当前 `s_axi_araddr` 选择 `quo/rem/done`，而 `RVALID` 由另一段时序逻辑保持。

| 时刻 | 主设备 / 运算模块 | 原版读数据 |
| --- | --- | --- |
| T0 | AR 握手接受读取 done，当前 done=0 | 选择 done |
| T1 | RVALID=1，RREADY=0；ARADDR 改变 | 可能切换为商或余数 |
| T2 | 即使 ARADDR 不变，内部 done 由 0 变为 1 | 同一未消费响应的数据也会改变 |

`RVALID` 保持只说明有未消费响应，不能保证响应内容没有变化。AR 通道在地址握手后可以继续变化，不应把当前 ARADDR 当作正在等待消费的 R 响应的地址。

## 3. 改了什么，为什么这样改

后续版本在 **ARVALID && ARREADY** 时把地址选中的返回数据存入 RDATA 寄存器，之后直到下一次接受读请求都不改写。复位时将 RDATA 清零。

只锁存地址仍不够：若读的是 done 等会变化的内部状态，数据源依然可能在反压期间变化。因此该修复锁存的是本次响应的数据快照。

该修改没有重写 AW/W、写响应控制或除法数据通路。寄存器读出的值对应请求被接受时的快照；主设备接受响应后再发新读，才看到新状态。

## 4. 怎样证明修改有效

新增公开测试在读 done=0 后保持 RREADY=0，并交替改变 ARADDR，持续 270 拍，期间真实除法器完成运算。

- 原版：测试在第 0 个等待周期发现 `held=0, actual=5`，失败。
- 修复版：整个等待区间返回值仍为 0，RVALID 保持；消费响应后重新读状态得到 1。
- 同时检查 AW/W 三种顺序、写反压、全零 WSTRB、真实商余数、ack、复位清理及复位后运行。

新增测试与修复必须按本次改进说明，不能倒写成原课程提交时已经完成。原 SVA TB 本次没有重跑。

## 5. 复盘表达

> 原始设计完成了 AXI4-Lite 接口与除法 IP 集成。后来补充读反压用例时发现，RVALID 虽然保持，RDATA 却直接依赖当前地址和运算状态，等待期间可能变化。我把返回数据改成在读地址握手时锁存，再通过同一测试对比原版与修复版；原版失败，修复版能够保持响应，并在下一次读取时返回更新后的状态。

只有理解了信号和验证过程后，才把这段作为自己的面试叙述；复盘时应能在原版、修复版和测试三份代码里定位对应逻辑。

## 6. 仍然保留的边界

- 除数 0 不支持，必须由软件避免；测试只是确认现有非终止行为并复位恢复。
- 65,280 组枚举针对运算核心，不是全部 AXI 事务组合。
- 50 LUT / 62 FF / 100 MHz 下 WNS 1.186 ns 属于原报告，修复后没有重新综合或实现。
- 没有 UVM、功能覆盖率统计或形式验证完成声明。
